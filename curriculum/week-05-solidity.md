# 第 5 周：Solidity 与最小积分合约

本周回答的问题是：**把业务规则写进智能合约，究竟写进了哪些状态、权限与失败条件？**

## 学习目标

完成本周后，你应当能够：

- 读懂 Solidity 合约的状态变量、映射、函数、事件、构造函数和可见性；
- 区分读取调用与产生交易的写入调用；
- 解释 `msg.sender`、`require`、自定义错误和访问控制的作用；
- 在本地环境部署配套积分合约，完成发行、转移与余额查询；
- 从接口、状态变化、事件和权限四个角度描述合约行为。

## 核心概念

### 1. 代码与状态

合约代码定义允许的状态转换；状态变量保存持久状态。`mapping(address => uint256)` 可以表达“地址 → 积分余额”，但映射不能自动列出所有持有人，也不会替你定义总量、转账或权限规则。

### 2. 调用者与权限

`msg.sender` 是当前调用层的直接调用者，不应被简单理解为永远等于最外层用户。仅创建者可发行的规则需要显式保存所有者地址，并在发行入口检查调用者。

### 3. 失败与原子性

前置条件不满足时，合约应回退该次调用造成的状态变化。清晰的失败条件既保护状态不变量，也让测试能够表达预期。交易失败仍可能消耗已经执行的计算资源。

### 4. 事件不是状态

事件用于通知链外索引器和界面发生了什么，便于检索；合约的当前余额仍应由状态变量决定。事件参数设计会影响链外研究的可查询性，但事件本身不能替代访问控制和状态校验。

## 实践

所有操作都在配套实验的本地开发网络中完成。本周不部署主网，也不要求公开测试网资产。

### 实践 A：建立源码地图

打开 `LearningPoints.sol`，但先不要修改：

1. 标出合约名称、编译器版本范围与许可证标识。
2. 找出所有持久状态变量，分别写出类型、初始值、谁能改变。
3. 找出发行与转移入口，列出参数、调用者、成功后的状态变化和失败条件。
4. 找出事件，解释每个参数与状态变化的对应关系。
5. 找出余额查询方式，判断它是显式函数还是公开状态变量自动生成的 getter。
6. 写出至少三个必须始终成立的不变量，例如“未被授权的地址不能增加任意账户余额”。

### 实践 B：编译并观察测试环境部署

1. 按 [实验 README](../labs/points-contract/README.md) 检查环境并安装依赖。
2. 运行 README 指定的编译命令，记录工具与编译器版本。
3. 运行完整测试；测试框架会为每个用例创建临时本地 EVM，不连接钱包或公共网络。
4. 打开测试文件，找到 `setUp()` 中的 `new LearningPoints()`；这就是每个测试开始前的本地部署。
5. 确认部署调用来自测试合约，因此新合约的 `owner` 是测试合约地址 `address(this)`。
6. 找出 `PointsActor`、`ALICE` 和 `BOB` 如何表示不同调用者/接收者；说明 `PointsActor` 为什么能改变内部调用的 `msg.sender`。
7. 记录测试数量与结果，并说明每个用例重新部署为何让用例之间不会共享余额。

### 实践 C：执行一个完整生命周期

用现有测试还原三个角色：测试合约是部署者 A，`PointsActor` 是普通调用者 B，`BOB`/`ALICE` 是接收地址 C。

1. 跟读 owner 发行 100 积分的测试，列出发行前后余额与 `Transfer` 事件。
2. 跟读 owner 先向 `PointsActor` 发行、再由 actor 向 `BOB` 转移 40 的测试，算出双方余额。
3. 对照 `vm.expectEmit`，确认预期事件的发出合约、索引参数和金额。
4. 跟读 actor 越权发行的测试，记录预期自定义错误并解释余额为何不应变化。
5. 跟读余额不足与零地址测试，分别指出检查发生在任何状态写入之前还是之后。
6. 将每个场景整理为“调用前状态 → 调用者与调用 → 结果/错误 → 调用后状态”。
7. 可选：在个人练习副本中新增一个单一生命周期测试，把发行、转移和最终余额断言串起来；第 6 周再系统扩展边界测试。

### 实践 D：读取与写入的区别

1. 找到 `balanceOf` 的 `view` 标记，并确认函数不会写入 `_balances`。
2. 找到 `transfer` 对 `_balances` 的两处写入和事件。
3. 区分两种情境：钱包/节点通过 `eth_call` 在链下模拟读取时不发送交易；另一个合约在链上调用 `balanceOf` 时仍处于某笔交易执行中并消耗 Gas。
4. 解释为什么公共网络上的写入需要交易、nonce、Gas 与共识纳入，而测试框架能在临时 EVM 中快速执行同样规则。

## 验收问题

1. 状态变量、局部变量和事件日志有什么区别？
2. `mapping(address => uint256)` 本身提供了哪些能力，没有提供哪些能力？
3. 为什么只保存 `owner` 地址还不够，发行函数仍需要权限检查？
4. `msg.sender` 在普通用户直接调用和合约间调用时可能有何不同？
5. 读取余额与转移积分在交易、Gas、nonce 和状态变化上有何区别？
6. 一个调用因余额不足失败后，先前执行的状态写入会怎样？
7. 为什么事件不能替代余额状态，也不能证明业务规则正确？

判断标准：不看源码也能列出合约的公开入口、每个入口的调用权限、成功状态变化和失败条件；能够用一次真实的本地执行记录验证说明。
