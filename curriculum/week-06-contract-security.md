# 第 6 周：智能合约测试与最小安全评审

本周回答的问题是：**如何证明一个合约在正常路径和失败路径上都更接近我们声称的行为？**

## 学习目标

完成本周后，你应当能够：

- 把需求改写成可执行的成功、失败和边界测试；
- 运行并解释配套合约的 Solidity 测试，而不是只看“全部通过”；
- 使用“检查—效果—交互”思路识别重入风险；
- 检查访问控制、零地址、余额不足、事件与状态不变量；
- 写出一份区分“已验证事实、合理推断、尚未验证”的最小安全评审。

## 核心概念

### 1. 测试是可重复证据，不是安全证明

单元测试只能覆盖被写出的场景。测试全部通过，说明当前代码在当前环境和这些输入下符合断言；它不能证明不存在未想到的路径、编译器问题、部署配置错误或经济攻击。

### 2. 成功、失败、边界与不变量

- 成功测试：合法发行、合法转移、正确事件；
- 失败测试：越权发行、余额不足、零地址；
- 边界测试：零金额、全部余额、最大合理数值、重复操作；
- 不变量：无论调用序列如何，都应持续成立的系统属性。

测试失败路径时，既要检查“调用确实回退”，也要检查状态没有发生部分改变。

### 3. 外部调用扩大攻击面

合约向不可信地址进行外部调用时，对方可能在原函数完成前回调。常见防御思路是先检查条件、再更新内部状态、最后进行外部交互，并根据场景使用重入保护。但“使用某个模式或库”不是自动安全，需要结合完整调用图分析。

### 4. 权限与升级权都是信任假设

只有 owner 可调用不等于去中心化，也不等于 owner 不会失误。研究时要问：谁控制 owner、能做什么、是否有延迟、多签或撤销机制、密钥丢失会怎样。本积分合约是教学最小模型，不应被当作生产代币实现。

## 实践

### 实践 A：建立需求—测试矩阵

先不用看测试文件，根据产品描述独立列出：

| 需求/不变量 | 初始状态 | 调用者与输入 | 预期结果 | 要检查的状态/事件 |
| --- | --- | --- | --- | --- |
| 仅创建者可发行 |  |  |  |  |
| 合法转移 |  |  |  |  |
| 余额不足必须失败 |  |  |  |  |
| 零地址规则 |  |  |  |  |
| 事件与状态一致 |  |  |  |  |

至少补充两个边界场景。完成后再与配套测试对照，标记“已有覆盖、部分覆盖、未覆盖”。

### 实践 B：运行并解释现有测试

1. 按 [实验 README](../labs/points-contract/README.md) 运行测试，记录工具版本、命令和结果。
2. 阅读 `test/LearningPoints.t.sol`，为每个测试写一句自然语言需求。
3. 对每个失败测试指出预期错误，以及失败后必须保持不变的状态。
4. 对事件测试指出发出者、事件名称和参数。
5. 暂时修改一项本地工作副本中的断言，使测试按预期失败；记录失败信息后恢复。不要把故意失败的修改提交为最终结果。
6. 解释为什么“测试能失败”是验证测试有效性的组成部分。

### 实践 C：补充边界测试

在个人练习分支或副本中至少补充两项：

- 转移恰好等于全部余额；
- 重复转移后的余额守恒；
- 零金额发行/转移的既定行为；
- owner 自己发行或转移的行为；
- 多账户调用序列后总发行量与余额和的一致性（若合约暴露足够状态）。

为每项测试先写预期，再写代码。若发现产品规则未定义，不要擅自把偏好当事实；在评审中记录为“规格缺口”。

### 实践 D：最小安全评审

按以下顺序审查主合约：

1. **资产与角色**：保护什么状态？普通用户和特权角色是谁？
2. **入口与权限**：哪些函数可由外部调用？谁能调用？
3. **状态不变量**：什么必须永远成立？整数溢出行为由哪个编译器版本决定？
4. **外部交互**：是否调用不可信合约？是否存在回调或重入面？
5. **错误路径**：零地址、余额不足、越权和意外输入如何处理？
6. **事件与可观测性**：关键状态变化能否被链外准确追踪？
7. **部署假设**：构造参数、owner 地址、编译器与网络是否可核验？
8. **范围边界**：当前没有发现的问题，不得写成“不存在风险”。

将发现分为：已确认缺陷、设计/信任风险、规格不清、超出本次范围。每条都附代码位置或测试证据。

### 实践 E：重入纸面推演

即使积分合约没有外部资产调用，也完成以下推演：

1. 画出“检查余额 → 向接收方外部调用 → 扣减余额”的危险顺序。
2. 让接收方在外部调用时重入，观察旧余额为何仍可被重复使用。
3. 改为“检查余额 → 扣减余额 → 外部调用”，重新推演。
4. 写出为什么改变顺序能降低该类风险，以及为什么仍需检查其他回调、授权和拒绝服务问题。

## 验收问题

1. 测试全部通过能证明什么，不能证明什么？
2. 为什么失败测试除了检查回退，还要检查调用后的状态？
3. `require`、`revert` 和 `assert` 在表达意图上有何区别？
4. 访问控制检查缺失与 owner 密钥被盗是同一种风险吗？
5. 重入发生需要什么调用条件？“检查—效果—交互”如何改变攻击顺序？
6. 事件参数正确但余额状态错误时，系统是否正确？
7. 什么是规格缺口？为什么评审者不应私自替产品补规则？
8. 为什么本教学合约不应直接用于生产资产？

判断标准：能任选一个测试，从需求、初始状态、调用、断言到被保护的不变量完整讲清；评审结论严格区分证据、推断和未知项。

## 安全提示

- 依赖安装和测试只在课程目录内进行，不以管理员权限运行来历不明的脚本。
- 本地开发密钥是公开测试凭据；不要复用于任何公共网络真实账户。
- 不把一次测试结果、静态扫描结果或审计报告理解为永久安全保证。
- 发现疑似漏洞时，不在主网合约上主动利用；保留最小证据并遵循项目披露政策。

## 离周门槛

由同伴随机挑一个失败条件，你能够先写出测试预期，再运行验证，并说明它保护的状态不变量。随后用 5 分钟讲清评审范围与至少一个仍未被测试消除的风险。
