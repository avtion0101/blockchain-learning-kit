# 基础实验：哈希、签名、区块引用与 UTXO

这些脚本使用 Node.js 内置模块，不安装第三方依赖、不联网，也不处理真实资产。示例中的链和 UTXO 规则是为了建立直觉而简化的模型，不是 Bitcoin 或 Ethereum 的完整实现。

## 运行

在本目录执行：

```powershell
npm test
npm run demo:crypto
npm run demo:ledger
```

也可以给密码学演示传入自己的消息：

```powershell
node crypto-demo.mjs "Alice pays Bob 10 units"
```

## 实验 A：哈希与签名

运行 `npm run demo:crypto`，观察：

1. 消息只增加一个句点，SHA-256 是否完全变化？
2. 原签名能否验证原消息？
3. 原签名能否验证修改后的消息？
4. 为什么签名能够证明“私钥持有者授权过某个具体消息”，却不能证明这个人现实中的身份？

修改 `crypto-demo.mjs` 的默认消息后再次运行。不要把签名理解成加密：消息仍然是公开的，签名解决的是授权与完整性问题。

## 实验 B：区块引用

运行 `npm run demo:ledger`。原链应通过验证；修改中间区块的一笔交易后，区块内容与原哈希不再匹配。

进一步尝试：

- 修改交易后重新计算该区块的哈希，观察下一个区块保存的 `previousHash` 为什么仍然失效。
- 同时重算所有后续区块，思考真实网络中为什么还需要共识与经济成本。仅有哈希链不能阻止攻击者在自己电脑上重写一条历史。

## 实验 C：UTXO 与双花

玩具账本最初给 Alice 一个金额为 10 的 UTXO。第一次交易将它消耗，产生 Bob 的 6、Alice 的找零 3，剩余 1 被视为手续费。再次引用原输入会被拒绝，因为它已经不在未花费输出集合中。

回答：

- 为什么“余额”可以由仍属于某个所有者的 UTXO 相加得到？
- 为什么找零必须成为一个新输出？
- 本地程序拒绝双花和整个网络就交易顺序达成一致，有什么区别？

## 验收

只有在不看代码也能解释以下三点时才算完成：

- 哈希证明数据未被改变，但不证明数据本身真实。
- 数字签名证明特定私钥授权了特定消息，但私钥泄露后攻击者也能签名。
- 区块引用让历史修改容易被发现；网络共识决定全体接受哪一条有效历史。
